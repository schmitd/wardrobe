# Wardrobe observability and product context

This is the durable operating contract for production feedback and product decisions. It applies to `main`, Vercel production deployments, and every preview deployment.

## Ownership boundary

| Signal | System of record | Why |
| --- | --- | --- |
| Product events, funnels, retention, flags, surveys | PostHog | Behavior and product decisions |
| Masked session replay and browser exceptions | PostHog | Reproduction with user-flow context |
| Server logs, traces, latency, failures, AI operations | Axiom | Operational debugging and performance |
| Priorities, decisions, owners, and resolution | GitHub issues | Durable work queue |

Do not mirror server logs or trace payloads into PostHog. Never send prompts, uploaded images, filenames, style-bio text, image-derived personal attributes, raw logs, authorization material, or full error payloads to PostHog. Replay masks all inputs and any element carrying `data-private`.

## Product event contract

| Event | Safe properties | Product question |
| --- | --- | --- |
| `guest_demo_analyzed` | `item_count` | Did a guest reach first value? |
| `guest_signup_prompted` | `source` | Where did the conversion prompt occur? |
| `wardrobe_item_added` | `content_type` | Are signed-in users activating their closet? |
| `compatibility_check_completed` | `category`, `verdict`, `score`, item counts | Is the core decision workflow used and useful? |
| `inspiration_saved` | `has_photo`, `collection_type` | Are users returning to product discovery? |
| `profile_bio_saved` | `character_count` | Are users personalizing recommendations? |
| `selfie_analyzed` | `has_color_season` | Is color-profile personalization completing? |
| `observability_smoke_test` | `smoke_id`, deploy URL, Git SHA, source | Does deployment ingestion work? |

Use `$pageview`, autocapture, and session replay for navigation and UI interactions instead of inventing click events. Keep event names in past tense for completed outcomes. Do not add IDs or free-form customer text as properties.

## Bug-feedback workflow

1. Create or update a GitHub bug issue using the repository template.
2. Record occurrence time with timezone, environment, route, and a privacy-safe affected-user scope.
3. Link the PostHog replay or exception and note the last successful product event. Do not paste replay contents.
4. Search Axiom around the same time for the route, operation, trace ID, and deployment SHA. Link the query or record only the trace ID.
5. Add severity, reproduction status, owner/next action, and acceptance criteria to the issue.
6. Close only after the fix is deployed and both the operational signal and user workflow are verified.

The browser trace ID generated by `createTraceContext` flows into server actions and Axiom. For scheduled smoke checks, `smoke_id` is the cross-system join key.

## Product-work workflow

Start with the PostHog dashboard, funnels, survey answers, and relevant masked replays. Capture the hypothesis and target metric in a GitHub product issue before implementation. During rollout, use a PostHog feature flag, define the exposure population, and retain a control where practical. Use Axiom only to ensure a product change did not degrade latency or reliability.

## Deployment and verification

Production and preview deployments both need:

- `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN`
- `NEXT_PUBLIC_POSTHOG_HOST`
- `AXIOM_TOKEN`
- `AXIOM_DATASET`

The web app proxies `/ingest/*` to PostHog, which keeps browser analytics first-party. After a deploy, pull the intended Vercel environment without committing it and run `bun run observability:smoke`. Then:

1. Search PostHog activity for `observability_smoke_test` and its `smoke_id`.
2. Search Axiom dataset `wardrobe-logs` for `event == "observability.smoke"` and the same `smoke_id`.
3. Open the deployed app and confirm a `$pageview`, a masked replay, and no new browser exception.
4. Exercise one server-backed workflow and confirm its Axiom trace carries the deployment SHA or trace ID.
